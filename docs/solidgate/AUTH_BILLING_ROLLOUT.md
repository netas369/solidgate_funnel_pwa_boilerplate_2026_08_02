# Authentication and billing recovery rollout — 2026-09-14

These changes are local boilerplate changes. No production auth configuration, user, session, card, subscription, or payment has been changed.

- Purchases still resolve and provision their account owner and preserve the signed OTO payment cookie. A checkout email does not create a browser login. The user must enter an emailed OTP, unless their existing session already proves the same confirmed email and account ID.
- `linkAuthUser` and `claim-purchase` no longer mint and immediately redeem administrative magic links. The funnel-to-PWA relay only accepts an already verified authenticated session.
- An anonymous funnel card remains scoped to its payment session and OTO journey. Promotion into the account vault requires the new `orders.auth_verified_at` marker, written only after a matching verified browser login or a successful OTP plus the current signed payment cookie. Account IDs and historical `claimed_at` values are not authentication proof. Generic email login never promotes all same-email checkout cards; another anonymous buyer may have supplied that address. SQL rejects both token and tokenless main-card writes before account-vault or subscription-sync mutations when this marker is absent; changing an order owner clears the marker.
- The new marker is deliberately **not backfilled**. Existing account cards and subscription-token jobs created by the old flow need a deployment-specific review alongside historical auth sessions; this local patch does not declare historical cards or claims verified. Authenticated PWA hosted-form cards (`pwa_order`) and leased card updates (`card_update`) retain their separate ownership/source checks.
- New paid users are created with `email_confirm: false`; local `[auth.email].enable_confirmations` is enabled. Configure **both** the Supabase Magic Link and Confirm Signup email templates to include `{{ .Token }}` for the six-digit login UI. Both local templates point to `supabase/templates/otp-email.html`. Existing hosted projects require these auth settings/template changes separately; SQL migrations do not apply them.
- Previously auto-confirmed users and issued sessions do not become mailbox-verified retroactively. Before production rollout, review accounts/sessions created by the old checkout flow. Affected sessions may need revocation and their owners must verify their mailbox again. This requires a deliberate environment-specific rollout; no blanket account/session mutation is performed by this patch.
- Paid content now requires a current main entitlement, finite grace, or lifetime purchase. A recently expired renewal gets a confirmation screen for at most 15 minutes; missing/expired entitlement and read failures do not open paid content. Billing recovery lives outside the paid-content route group at the same `/billing/update-payment` URL.
- A genuinely canceled main subscription has no existing billable subscription for card recovery. Its locked screen routes to support or sign-out, without implying that replacing a card restores access. **Full-price main resubscription after an already consumed intro remains a product feature gap**: current main checkout tiers are introductory; there is no self-service full-price restart route. The provider restore client is not exposed as a browser action.
- A past-due or expired add-on with an existing billable subscription opens payment-method recovery instead of reporting ownership or creating a second subscription. Updating a card never restores access by itself: a successful renewal remains the payment proof.
- Card-update UI requires the final `{ok:true}` payload; HTTP 202 remains pending. The shared durable recovery worker checks the same issued zero-auth order and uses the existing vault/consume claim fences. The internal cron must drain card updates before subscription token synchronization.
- Disabled checkout locales are rejected before provider checkout creation; currency never silently falls back to English/USD. Saved-card add-on intro verification and analytics use the bound nonzero intro price.

Regression coverage includes existing-account checkout email impersonation and account-card poisoning, unverified new emails, mismatched signed-in identities, verified claiming of prelinked purchases, OTP card promotion restricted to its current purchase cookie, native Fetch HTTP 202 semantics, browser-independent card reconciliation, add-on recovery without a second purchase, expiry/read-error access boundaries, and locale/intro amount consistency. All provider and auth operations in these tests are mocked; no paid services are called.
