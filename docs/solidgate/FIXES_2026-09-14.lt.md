# Solidgate audito pataisos — 2026-09-14

Šis dokumentas aprašo **šio boilerplate vietines pataisas** po [2026-09-14 audito](AUDIT_2026-09-14.lt.md). `theastrologist` production naudotas tik ankstesniam palyginimui: šio darbo metu jo DB, paskyros, mokėjimai ir diegimai nekeisti. Pirminis auditas paliktas kaip prieš pataisas nustatytos būsenos įrodymas.

## Prisijungimo spraga paprastai

Anksčiau žmogus galėjo checkout įrašyti svetimą el. paštą ir sumokėti savo kortele. Jei tam adresui nebuvo suveikęs intro ribojimas, kodas sugeneruodavo administratoriaus magic link ir pats jį patvirtindavo. Naršyklė gaudavo prisijungimą prie to el. pašto paskyros, nors mokėtojas neturėjo prieigos prie pašto dėžutės.

Dabar pirkimas priskiriamas paskyrai, tačiau checkout ir `claim-purchase` nebeišduoda tokios prisijungimo sesijos. Prisijungimui reikia į el. paštą išsiųsto OTP arba jau turimos patvirtintos, sutampančios vartotojo sesijos. OTO tęstinumas išlieka per pasirašytą mokėjimo slapuką. Naujos paskyros nebežymimos automatiškai patvirtintomis. Paskyros kortelės saugykla taip pat negali būti atnaujinta vien pagal checkout el. paštą: `orders.auth_verified_at` atskirai žymi serverio patikrintą sutampančios paskyros prisijungimą. Senas `claimed_at` nėra tokio patvirtinimo įrodymas. Iki patvirtinimo kortelė lieka konkrečios checkout sesijos srautui. [Auth ir billing diegimo detalės](AUTH_BILLING_ROLLOUT.md).

## Kur dabar ieškoti pinigų ir laikotarpių

| Lentelė / view | Paskirtis |
| --- | --- |
| `orders` | Vienas checkout / pirkimo bandymas, nekintantis kainos ir tapatybės susiejimas, dabartinė projekcija. `amount_cents` negali būti naudojamas kaip visas finansinis žurnalas. |
| `renewal_events` | Dabartinė renewal projekcija, susieta su provider order ir invoice. |
| `solidgate_payment_balances` | Kiekvieno provider order quoted, captured, refunded, chargeback ir net sumos; invoice / subscription ryšiai ir apmokėtas laikotarpis. |
| `solidgate_financial_movements` | Nekeičiami finansiniai pokyčiai su signed delta, įvykio data ir datos įrodymo tipu. Unikalus environment + event key + provider order apsaugo replay. |
| `solidgate_capture_transactions` | Atskirų patvirtintų capture transakcijų ID ir sumos, kad daliniai settle nesidubliuotų ir būtų sumuojami. |
| `solidgate_subscription_snapshots` | Naujausia provider subscription būsena, pradžia, trial, kitas mokėjimas, atšaukimas, periodas. |
| `solidgate_subscription_history` | Nekeičiami subscription callback faktai ir jų provider datos. |
| `solidgate_reconciliation_issues` | Istorinės apytikslės sumos, trūkstami ryšiai / periodai, refund virš žinomo capture ir nepatvirtintos operacijų datos. |
| `solidgate_webhook_events` | Gautas ir patikrintas raw payload, apdorojimo būsena bei klaida. |

Sumos laikomos **tos valiutos mažiausiais vienetais**: USD / EUR centais, JPY jenomis. EUR ataskaita yra perskaičiavimo įvertis pagal sukonfigūruotus kursus. Tai nėra banko išmokų, komisinių ar settlement valiutos apskaita.

Current net balansas: `max(0, captured - max(refunded, active_chargeback))`. Finansiniai delta gali būti neigiami, pavyzdžiui refund atėjus anksčiau už capture; tai išsaugo datuotą pinigų judėjimą ir pažymi nepakankamą capture įrodymą sutikrinimui. Analytics `payment_captured` yra dalinio capture diagnostika: jis neturi `revenue` lauko, kad dalinis ir galutinis pirkimo įvykiai nedubliuotų sumos. Finansinės ataskaitos remiasi DB judėjimų žurnalu.

Chargeback `resolved` nėra laimėtas ginčas: rezervą grąžina tik `reversed` / `resolved_reversal`.

## DB užklausos operatoriui

Tik skaitymas, naudojant teises turinčią vidinę prieigą. Visada pasirinkti teisingą aplinką ir nelaikyti visų valiutų vienais eurais.

```sql
-- Visa konkretaus žmogaus faktinė pinigų istorija.
SELECT occurred_at, occurred_at_source, currency, solidgate_order_id,
       captured_delta_cents, refunded_delta_cents,
       chargeback_delta_cents, net_delta_cents, evidence_source
FROM public.solidgate_financial_movements m
WHERE m.environment = 'production' AND (m.user_id = '<USER_UUID>'::uuid
  OR m.order_id IN (SELECT id FROM public.orders WHERE user_id = '<USER_UUID>'::uuid))
ORDER BY occurred_at, recorded_at, id;

-- Kada prasidėjo trial, kada keitėsi periodas ir prenumeratos būsena.
SELECT event_created_at, event_type, solidgate_subscription_id, facts
FROM public.solidgate_subscription_history h
WHERE h.environment = 'production' AND (h.user_id = '<USER_UUID>'::uuid
  OR h.order_id IN (SELECT id FROM public.orders WHERE user_id = '<USER_UUID>'::uuid))
ORDER BY event_created_at, recorded_at, id;

-- Neužmirštamos spragos: sumos/datos, kurias dar reikia sutikrinti.
SELECT issue, count(*)
FROM public.solidgate_reconciliation_issues
WHERE environment = 'production'
GROUP BY issue;

-- Klaidos negali būti painiojamos su sėkmingai apdorotais mokėjimais.
SELECT type, status, count(*)
FROM public.solidgate_webhook_events
WHERE environment = 'production' AND status <> 'completed'
GROUP BY type, status;
```

Jei mokėjimo istorijos `user_id` dar tuščias, susiejimą galima rasti per `order_id → orders.user_id`. Provider invoice / subscription ID laikomi papildomam tiksliam sutikrinimui; el. paštas nėra finansinio įvykio identifikatorius.

## Diegimo seka ir tikros ribos

1. Naujam boilerplate projektui visas schema yra `00001_baseline.sql`. Jau veikiančiam projektui skirti papildomi `20260914070652_financial_event_ledger.sql` ir `20260914070819_solidgate_financial_reporting.sql`. Pirmiausia schema, paskui suderinti webhook ir abu app leidimai. DB tipai generuojami iš tikros vietinės schemos.
2. Senų duomenų migracija sukuria pažymėtus `legacy_projection` įrašus. Ji **neatkuria neegzistuojančių raw capture, refund ar settlement datų**. Istorinius duomenis reikia sutikrinti su Solidgate operacijomis / eksportu; tokie duomenys ataskaitose aiškiai pažymėti.
3. Abiejų app ir Edge Function `INTERNAL_API_SECRET` turi sutapti atitinkamoje aplinkoje. Cron GET `/api/internal/solidgate-fulfillment` kas 5 minutes kartoja išsaugotus webhook, užbaigia kortelių atnaujinimus, fulfillment ir tokenų sinchronizaciją. Jei Edge Function pavadinimas skiriasi, nustatyti `SOLIDGATE_WEBHOOK_RECOVERY_URL`. Endpoint prieš replay patikrina tikėtiną aplinką.
4. POST į tą patį app endpoint paliktas greitam webhook inicijuotam fulfillment; jis nesukuria rekursyvaus recovery ciklo. Vienos eilės klaida nesustabdo kitų; atsakymas rodo nesėkmę, kai bent viena eilė neužbaigiama.
5. Hosted Supabase el. pašto confirmation ir OTP šablonai keičiami atskirai nuo SQL. Anksčiau auto-confirmed paskyros / išduotos sesijos netampa retrospektyviai patvirtintomis. Jų peržiūra ir reikalingas atsijungimas yra atskiro konkrečios aplinkos išleidimo dalis.
6. Pagrindinio plano pakartotinis pirkimas pilna kaina po tikro atšaukimo dar nėra įgyvendinta produkto funkcija: visi esami funnel main pasiūlymai yra intro. Atšauktam main nerodomas klaidinantis pažadas, kad kortelės pakeitimas atkurs prenumeratą; rodomas support kelias. Naujos kainodaros / provider produkto šios pataisos neprideda.
7. Naujo produkto Solidgate kainos / provider ID vis tiek turi būti sukonfigūruoti jo kataloge. Ši pataisa nekuria mokamų provider produktų ir nepakeičia paties produkto prenumeratos kainodaros.

## Patikra

Pataisoms naudojami lokalūs Vitest / TypeScript ir tikras izoliuotas PostgreSQL. Finansinės permutacijos tikrina refund prieš capture, mažėjantį pakartotinį refund, refund su chargeback, atstatymą, dalines capture transakcijas ir outbox rollback. Ataskaitų SQL testas turi 1101 mokėjimą, dvi valiutas, atšauktus konvertavusius klientus ir skirtingas renewal / refund datas. Esami konkurencijos testai tikrina tikrus lygiagrečius DB užraktus.

**Galutiniai rezultatai:** 1642 Vitest testai (funnel 1032, PWA 249, shared 361), abiejų app TypeScript ir webhook Deno patikros praėjo. Visi 11 SQL rinkinių praėjo; abu konkurencijos rinkiniai pakartoti (13 SQL vykdymų). Atskirai praėjo migracija su 8 senų pradinių / renewal mokėjimų atvejais ir jos pakartojimas, išsaugant sumas bei istoriją.
